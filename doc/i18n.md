# data/i18n/ — convention

Données de traduction, éclatées par **domaine fonctionnel** — un fichier par grand
domaine du jeu, un dossier par langue. Le moteur générique (`createI18n`) vit dans
`lib/i18n.js` et `lib/i18n/message.js` (voir "Grammaire des textes") ; ce dossier ne
contient que des **données**.

Chaque fichier-domaine est du **JSON pur** (`.json`, pas `.js`) : le format lui-même
interdit toute logique — aucun risque qu'un fichier de traduction accumule un jour du
code. Lisible nativement par n'importe quel outil (Python compris, pour une future
vérification de parité automatisée), cohérent avec le reste de `data/` et avec les
scènes (`scenes/*.json`).

```
data/i18n/
  index.js      # liste des domaines (DOMAINS, la même pour toutes les langues),
                # charge chaque langue (fetch, lib/i18n.js/loadLocale) et instancie
                # lib/i18n.js — POINT D'ACCÈS UNIQUE, importé par toute la vue
                # (view/**, main.js) via `import { t } from ".../data/i18n/index.js"`.
  grammar.json  # formes et attributs de nom reconnus par chaque langue (voir
                # "Grammaire des textes") — pas un domaine de clés.
  fr/
    <domaine>.json   # un fichier par domaine, contenu de chacun dans la table
                     # "Où va une nouvelle clé"
  en/
    (mêmes noms de fichiers .json EXACTEMENT — voir "Parité" plus bas)
```

Seul `index.js` est en JavaScript : c'est le MÉCANISME de chargement (fetch +
assemblage), jamais de la donnée. Les fichiers-domaines
eux-mêmes, `.json`, ne contiennent RIEN d'autre que des paires clé-valeur.

## Où va une nouvelle clé

Chaque fichier-domaine correspond à un **espace de noms de clé** (le préfixe avant le
premier point, avec quelques regroupements assumés — voir la table). Trouve le préfixe
de ta clé, ajoute-la dans **les deux langues**, même fichier.

**Entités et objets : un namespace, des feuilles.** Tout ce qui concerne une
entité ou un objet (nom, description, messages de refus...) vit en feuilles sous
SON namespace (`entity.glass_window.name`, `entity.glass_window.description`) —
jamais une clé plate `entity.glass_window` qui ferait double emploi avec le dossier
`entity.glass_window.*`. (Les libellés de menus, eux, ont une `.description` sous leur
propre clé : convention différente, assumée.)

| Domaine | Fichier | Contenu |
|---|---|---|
| Menus | `menus.json` | Chrome générique de menu (`menu.position`, `menu.toggle.*`, `menu.confirm.*` — voir `view/menus/confirmation.js`), menu principal (`menu.main.*`), pause (`menu.pause.*`), le SHELL Options (`menu.options.*` : titre, entrées de navigation, réinitialisation globale — jamais le contenu d'un sous-écran) |
| Interaction | `interaction.json` | Menu de désambiguïsation (`menu.interaction.*`), retours ramassage/butin (`interaction.*`) |
| Inventaire | `inventory.json` | Sac (`inventory.*`), équipement (`inventory.equipment.*`, `equipment.slot.*`) |
| Objets | `items.json` | Registre d'objets (`item.*`, `core/items.js`) et leurs tags (`tag.*`) — DISTINCT de `entities.json` : un objet ramassable, pas un type d'entité |
| Audio | `audio.json` | Sous-écran Options > Audio (`menu.audio.*`, `audio.*`) |
| Navigation | `navigation.json` | Sous-écran Options > Navigation (`menu.navigation.*`) — inclut l'affichage des coordonnées de la carte (réglage, pas contenu) |
| Sauvegarde | `save.json` | Sous-écran Options > Sauvegarde (`menu.save.*`) + mécanisme de sauvegarde/import partie (`save.*`) |
| Statut | `status.json` | Annonces d'état à la demande (`time.*`, `money.*`, `position.*`, `side.*`) + vocabulaire calendaire (`time.season.*`, `month.*`, `weekday.*`) |
| Scènes | `scenes.json` | Noms de scène (`scene.<id>.name`, convention OBLIGATOIRE : la confirmation d'une sortie la lit sans charger la scène, voir `doc/scripting.md`/"Confirmation d'une action" ; vérifiée par `tools/content-audit.js`), annoncés à l'arrivée et par Retour arrière. Base SANS article (« grand-place », « ruelle ») ; une scène principale porte en plus sa forme `def` (« la grand-place », « Main Street »), que demande la confirmation de voyage |
| Entités | `entities.json` | Types d'entité (`entity.*`), familles d'entités à textes par instance (`door.*`, `passage.*`, `scene_exit.*`, `mirror.*`, `magic_mirror.*`, voir ci-dessous), instances spécifiques (`object.*`, `npc.*`) — chaque type/instance est un NAMESPACE, jamais une clé plate : nom sous `<namespace>.name`, description sous `<namespace>.description` (voir `entity.nameKey`/`descriptionKey`, `doc/entity-model.md`) |
| Carte | `map.json` | Carte de la ville (`cityMap.*`) |
| Perception | `perception.json` | Perception surnaturelle (`perception.*`) |
| Météo | `weather.json` | Moteur météo (`weather.*`) — noms d'état + gabarit d'annonce (voir core/weather.js) |
| Collections | `collections.json` | Onglet Collections et annonce de découverte (`collections.*`), textes des collections et de leurs entrées (`collection.<id>.name`, `collection.<id>.entry.<objet>.name`/`.description`, déduits des ids — voir `doc/collections.md`) |
| Boutique | `shop.json` | Point de vente (`shop.*`) : menu d'actions, menu à sliders commun (`shop.adjust`, `shop.detail`, `shop.list.*`, `shop.discard.*`), vente (`shop.sell.*`), achat (`shop.buy.*`) — voir `view/menus/shop-menu.js` |

### Familles d'entités : l'espace de clés porte le nom du type

Un type dont les instances ont souvent leurs PROPRES textes (une porte précise,
un passage précis) a son propre espace de clés, au nom du type, au lieu de
`entity.*` :

- `<type>.default.name` / `.description` (et autres feuilles, ex.
  `magic_mirror.default.pass_refusal`) : les textes de l'archétype, hérités par
  toute instance qui ne déclare rien ;
- `<type>.<instance>.name` / `.description` : les textes propres à une instance,
  déclarés dans la scène via `nameKey`/`descriptionKey` (ex.
  `passage.town_hall.description`). Une instance ne redéclare jamais une clé qui
  ne ferait que répéter le défaut.

Familles actuelles : `door`, `passage`, `scene_exit`, `mirror`, `magic_mirror`. Un type de la
famille `door` (échelle, par exemple) garde `door.*`. Les autres types restent
sous `entity.<type>.*`. Renommer une clé : voir `doc/save.md` (table
`config/save-renames.js`).

Aucune clé ne doit apparaître dans deux fichiers-domaines de la même langue (chaque
domaine est un espace de noms disjoint) — `data/i18n/index.js` les assemble par
simple fusion (`Object.assign`, voir `lib/i18n.js`/`loadLocale`), un doublon
écraserait silencieusement l'un des deux.

Un domaine qui grossit trop, ou une nouvelle famille de clés qui ne rentre nulle part
proprement : crée un nouveau fichier plutôt que de forcer un domaine existant — même
règle que l'inverse (ne jamais créer un fichier pour une poignée de clés qui ont
clairement leur place ailleurs).

## Casse : noms en minuscules, phrases normales

Les **noms** s'écrivent en minuscules : tout ce qui désigne une chose et peut
s'insérer dans une phrase — `<namespace>.name` (entités, portes, objets, scènes,
collections et leurs entrées, améliorations), libellés d'objets
(`item.combat_boots.name`), emplacements d'équipement (`equipment.slot.*`),
étiquettes (`tag.*`), mois, jours, saisons, états météo. Seule exception : un
mot qui garde sa majuscule partout — sigle (`LED`, `EPROM à fenêtre`) ou nom
propre (`Hall effect sensor`, `statue de Matasîle`).

Les **descriptions** et autres textes sont des phrases correctes, majuscule et
point compris. Les **formes** d'un nom (`def`...) s'écrivent comme en milieu de phrase,
noms propres compris (voir "Grammaire des textes").

La majuscule de tête est remise à la SORTIE, en un seul point :
`lib/announce.js` met une majuscule au début de chaque PHRASE de l'annonce —
en tête du texte et après « . », « ! », « ? » ou « … ». Un nom qui ouvre une
ligne (« pomme : un fruit. ») s'annonce donc « Pomme : un fruit. », et une
entrée de menu assemblée (« Observer. ordinateur cassé. 1 sur 2 ») s'annonce
« Observer. Ordinateur cassé. 1 sur 2 », sans qu'aucun écran ni gabarit n'ait
à s'en soucier. Après « : » ou « , », le nom reste en minuscules. Un marqueur de tête
qui n'est ni lettre ni chiffre (l'étoile de limite des menus, un guillemet) est sauté :
« * pomme » s'annonce « * Pomme ».

## Typographie et ponctuation

### Ponctuation propre à chaque langue

Toute ponctuation qui DIFFÈRE entre nos langues vit dans un gabarit, jamais dans le
code. Clés de contrat de `lib/menu.js` (la langue doit les fournir) :

| Clé | Rôle | fr | en |
|---|---|---|---|
| `menu.position` | position d'une entrée | `{index} sur {total}` | `{index} of {total}` |
| `menu.described` | libellé suivi de sa description | `{text} : {description}` | `{text}: {description}` |
| `menu.skipped` | entrées sautées par Ctrl+flèche | pluriel | pluriel |
| `menu.toggle.yes` / `.no`, `menu.message.ok` | valeurs et bouton | | |

La carte a la sienne, `cityMap.zone` (`{name} : {description}`). Une nouvelle ligne
« quelque chose : sa description » passe par `menu.described` ou un gabarit à elle,
jamais par `` `${a} : ${b}` `` dans le code.

### Guillemets

Jamais les guillemets droits du clavier (`"`) : « » en français, “ ” en anglais.
`tools/check_i18n_parity.py` signale tout guillemet droit, dans toutes les langues,
sans le corriger d'office (il ne peut pas deviner lequel ouvre et lequel ferme).

### Espaces insécables du français

Espace insécable (U+00A0) avant « : » et à l'intérieur des guillemets « », espace fine
insécable (U+202F) avant « ; », « ! » et « ? ». On tape des espaces ORDINAIRES dans
les fichiers (une insécable est invisible dans un éditeur) :
`tools/check_i18n_parity.py` signale chaque espace ordinaire à ces places, et `--sort`
la remplace (règle `TYPOGRAPHY` de l'outil, par langue). Pour la synthèse vocale, rien
ne change ; une plage braille ne coupe plus la ligne juste avant le signe. Les
constantes des vérifications s'écrivent échappées (`"\u00a0"`), jamais avec le
caractère lui-même.

### Hypothèse assumée : écriture latine

Le reste de l'assemblage des annonces suppose une écriture LATINE (ou cyrillique,
grecque) : phrases terminées par « . ! ? … » et séparées par une espace, virgule et
deux-points occidentaux. Juste pour le français, l'anglais, l'allemand, l'espagnol, le
russe ; faux pour le chinois ou le japonais (« 。 » sans espace, virgule « 、 »), l'arabe
(« ، », « ؟ »), etc. Rien de tout cela n'est migré tant qu'aucune de ces langues n'est
visée — mais tout est recensé ici, pour que ce jour-là le chantier soit déjà cartographié.

| Hypothèse | Où | Ce qui changerait |
|---|---|---|
| Deux phrases jointes par « . » + espace | `lib/menu.js` : titre puis entrée (`buildOpenAnnouncement`), entrée puis position (`actionLine`), « 3 éléments ignorés » puis entrée (`moveCursorSkipping`) ; `view/menus/shop-quantity-list.js` : ligne puis suffixe, titre puis ligne (×2) | une clé de contrat `menu.sentences` (`{first}. {second}`) fournie par chaque langue |
| Phrases jointes par une simple espace | `view/collection-discoveries.js` (découvertes), `view/menus/inventory/bag-and-equipment.js` (« Équipé : … » puis le retrait du sac, deux endroits) | même clé, ou un gabarit par annonce |
| Une description se termine par « . », retiré quand une suite vient derrière | `lib/announce.js/stripTrailingPeriod` et ses appelants (une vingtaine, `grep stripTrailingPeriod`) | la ponctuation finale fournie par la langue, ou des descriptions sans point final |
| Une fin de phrase est « . ! ? … » | `lib/announce.js/capitalizeSentences` (majuscule de début de phrase) ; `lib/menu.js/buildOpenAnnouncement` (titre déjà ponctué : pas de second séparateur) | le jeu de signes fourni par la langue ; une écriture sans casse n'a de toute façon rien à capitaliser |
| Libellé et valeur séparés par une virgule | `lib/menu.js/buildValueLine` (« Volume, 50 »), et « libellé, valeur. » sans description | dans `menu.described` ou une clé `menu.value` |
| Noms énumérés par des virgules | `view/occupancy.js` (annonce de proximité) — laissé tel quel, `{list}` possible | `{names, list}` (Intl.ListFormat) |

Les coordonnées de la carte (« A - 1 », `lib/coordinate-label.js`) et la jointure des
modificateurs clavier (`lib/input.js`) ne sont pas du texte de langue.

## Langue de l'interface

Réglage Options > Langue (préférence `locale`, `config/preferences.js`), en tête du
menu Options : « Automatique » (la langue du navigateur, si le jeu la fournit, sinon la
langue de repli) ou une langue précise. Chaque langue est nommée dans SA langue
(« Français », « English »), lisible quelle que soit celle de l'interface. Les valeurs
du réglage sont "auto" puis exactement les langues chargées par `data/i18n/index.js`,
vérifié par le domaine `i18n` des vérifications.

`view/locale.js`/`applyLocalePreference` applique le réglage au moteur ET à la page :
attribut `lang` du document (le lecteur d'écran en tire sa voix et sa prononciation :
un texte anglais sous `lang="fr"` serait lu avec la voix française), titre de la page
et nom de la zone de jeu (`aria-label` de `#game`). Appelée au démarrage (`main.js`),
à chaque changement du réglage, après « Réinitialiser tous les réglages » et après un
import de préférences. Rien d'autre à rafraîchir : tout texte passe par `t()` au moment
de son annonce, aucun texte traduit ne reste écrit dans la page.

Ajouter une langue : son dossier `data/i18n/<langue>/` (mêmes fichiers), son entrée
dans `data/i18n/index.js` et `data/i18n/grammar.json`, sa valeur dans
`PREF_CONSTRAINTS.locale.values` et son libellé `menu.options.language.<langue>` dans
chaque langue.

## Parité fr/en

**Même nom de fichier des deux côtés, toujours** (`fr/inventory.json` ↔
`en/inventory.json`) — c'est ce qui rend une vérification de parité triviale : les deux
dossiers doivent lister exactement les mêmes fichiers, et chaque paire doit porter
exactement le même ensemble de clés (valeurs différentes, bien sûr — c'est le but).
Une clé ajoutée dans une langue sans son pendant dans l'autre est un bug de contenu,
détectable par un simple diff de clés fichier par fichier — en JSON pur, ce diff peut se
faire avec n'importe quel outil, y compris hors JavaScript (Python, jq, etc.).

**Outil de vérification** : `tools/check_i18n_parity.py` (langue de référence `fr`) —
liste précisément les clés manquantes/orphelines/vides par fichier, écrit un rapport,
code de sortie non nul si une divergence existe. À lancer après tout ajout/renommage de
clé, avant de considérer une tâche touchant l'i18n comme terminée. Une valeur VIDE dans
toutes les langues est un silence voulu (ex. `weather.transition.clear.end`, un fragment
d'annonce que le jeu omet), jamais une divergence ; vide dans une seule langue, c'est une
traduction manquante. Un nom écrit en objet de formes est vide si sa `base` l'est ;
ses autres formes sont propres à chaque langue et ne se comparent jamais.

**Mêmes paramètres dans chaque langue** : une clé utilise les mêmes noms de paramètres
d'une langue à l'autre (« {count} » partout, jamais « {cout} » dans une seule), branches
comprises. Vérifié par le domaine `i18n` des vérifications (`node tools/run-checks.js
i18n`, avec le vrai analyseur des gabarits, `lib/i18n/message.js`/`messageParams`),
contre le français. Les formes de nom (`{scene:def}`) et les catégories de pluriel
restent libres : seule compte la liste des paramètres. Une faute de ce genre passe le
chargement (le gabarit est valide), puis s'annoncerait telle quelle en jeu : la
vérification l'arrête avant.

**Typographie** : en français, `--sort` pose aussi les espaces insécables (voir
"Typographie et ponctuation"), et une espace ordinaire à leur place est une divergence.

**Clés triées par ordre alphabétique**, dans chaque fichier : chaque famille de clés
(`door.*`, `entity.*`, `passage.*`...) reste ainsi d'un seul bloc, facile à parcourir.
Un fichier non trié est une divergence pour l'outil. Pas besoin de chercher la bonne
place à la main : ajoute la clé n'importe où, puis lance
`python tools/check_i18n_parity.py --sort`, qui réécrit les fichiers dans l'ordre
attendu (même format) avant de vérifier.

## Grammaire des textes

Moteur : `lib/i18n.js` (chargement, langues, `t`) et `lib/i18n/message.js` (analyse et
rendu des gabarits). Vérifications : `node tools/run-checks.js i18n`
(`lib/checks/i18n.check.js`), qui servent aussi d'exemples exécutables.

### Dialecte

Les gabarits suivent la syntaxe **ICU MessageFormat classique** (dite MF1) pour
`plural`, `selectordinal` et `select`. Trois éléments sont des **extensions propres à
ce moteur**, pas du standard ICU : les formes de nom (`{scene:def}`), le choix sur un
attribut de nom (`{item:gender, select, …}`) et le type `list`. Seul le sous-ensemble
décrit ici est reconnu ; tout le reste est refusé au chargement.

**Pourquoi pas MessageFormat 2.** Unicode a stabilisé en 2025 une nouvelle syntaxe,
MF2 (`.match $count one {{…}} * {{…}}`), plus puissante : nos formes de nom y seraient
des fonctions personnalisées. On reste sur la syntaxe classique : nos gabarits sont des
phrases d'une ligne, que MF2 rendrait verbeuses ; c'est la syntaxe que connaissent les
outils et les traducteurs ; aucun navigateur ne fournit MF2 nativement aujourd'hui. Le
sous-ensemble se transpose sans perte vers MF2 si l'on migre un jour (`plural`/`select`
deviennent `.match`, les formes une fonction).

### Écart volontaire avec ICU : apostrophes et accolades

- **L'apostrophe est toujours littérale.** En ICU, `'` échappe ; ici, jamais. « l'hôtel »,
  « aujourd'hui », « c'est {scene:def} », « {name}'s office » s'écrivent tels quels.
- **Aucun mécanisme d'échappement.** Une accolade isolée, ouvrante ou fermante, ou un
  bloc mal fermé est une **erreur au chargement**, qui nomme la langue et la clé. Aucun
  texte n'a besoin d'une accolade littérale aujourd'hui ; si le cas arrive, on ajoutera
  un mécanisme ce jour-là.
- **`#` n'a de sens que dans une branche** de `plural` ou de `selectordinal`, où il vaut
  toujours le nombre. Ailleurs, c'est un `#` littéral.

### Paramètres simples

`{nom}` insère la valeur du paramètre :

| Valeur passée par le code | Rendu |
|---|---|
| chaîne | telle quelle (ex. `"12.50"`, la position en debug, n'est jamais reformatée) |
| nombre | `Intl.NumberFormat` de la langue : « 1 000 000 » (fr, espace fine insécable), « 1,000,000 » (en), « 0,5 » (fr) |
| référence de nom (`nameRef("scene.town_square.name")`) | sa forme `base` |

Un paramètre absent est laissé tel quel dans le texte (`{scene}`) et signalé en console,
jamais une exception.

### Pluriel — `plural` (ICU)

```
{n, plural, =0 {…} one {…} other {…}}
```

- Seule **`other` est obligatoire**.
- Une catégorie que **la langue ne connaît pas** est une **erreur au chargement**
  (`few` en français). Les catégories viennent de `Intl.PluralRules(langue)`.
- `=N` vise un nombre exact et passe avant les catégories ; `offset:` n'est pas reconnu.
- `#` vaut `n`, formaté par `Intl.NumberFormat`.

Catégories des langues actuelles : **français** `one` (0 et 1), `many` (millions ronds :
1 000 000, 2 000 000…), `other` ; **anglais** `one` (1), `other` (0 compris). Le `many`
français porte le « de » :

```json
fr  "{amount, plural, one {# pièce} many {# de pièces} other {# pièces}}"
```

→ « 0 pièce », « 1 pièce », « 2 pièces », « 1 000 000 de pièces », « 1 000 001 pièces ».

### Ordinaux — `selectordinal` (ICU)

Même forme que `plural`, sur les règles ordinales de la langue (`Intl.PluralRules`,
`type: "ordinal"` ; français `one`/`other`, anglais `one`/`two`/`few`/`other`) :

```json
fr  "{day, selectordinal, one {#er} other {#}} {month}"                         → 1er janvier, 2 janvier
en  "{month} {day, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}"   → January 1st, 2nd, 3rd, 11th, 22nd
```

### Choix — `select` (ICU)

```
{x, select, a {…} b {…} other {…}}
```

`x` est un paramètre chaîne ; `other` est obligatoire, et reçoit toute valeur sans
branche. **Extension** : `{item:gender, select, f {…} other {…}}` choisit sur un
**attribut** du nom passé en référence ; les branches sont limitées aux valeurs
déclarées pour cet attribut (voir plus bas).

### Formes de nom (extension)

Une clé de nom vaut soit une **chaîne** (équivalente à `{ "base": "…" }`), soit un
**objet de formes** : `base` obligatoire et non vide, plus des **formes** et des
**attributs** déclarés pour cette langue.

```json
fr  "scene.town_square.name": { "base": "grand-place", "def": "la grand-place" }
en  "scene.town_square.name": { "base": "town square", "def": "the town square" }

fr  "interaction.travelConfirm": "Partir vers {scene:def} ?"
en  "interaction.travelConfirm": "Head to {scene:def}?"
```

```js
t("interaction.travelConfirm", { scene: nameRef("scene.town_square.name") })
// fr -> "Partir vers la grand-place ?"   en -> "Head to the town square?"
```

- Le code passe une **référence** (`nameRef`, exporté par `data/i18n/index.js`), jamais
  un texte déjà traduit : c'est le gabarit de chaque langue qui choisit la forme.
- `t("scene.town_square.name")` rend la `base` : les usages directs (titre annoncé à
  l'arrivée, carte) ne changent pas.
- Traduction **asymétrique** : chaque langue déclare les formes dont SES gabarits ont
  besoin, une autre langue n'a rien à ajouter.
- Une forme demandée mais absente du nom : repli sur la `base`, signalé en console.
  En amont, l'audit du contenu (`tools/content-audit.js`/`NAME_SLOTS`) vérifie, pour
  chaque gabarit qui reçoit un nom par référence, que tous les noms qu'il peut recevoir
  portent toutes les formes qu'il demande, dans chaque langue. Un nouvel appel de
  `nameRef` dans la vue ajoute sa ligne à `NAME_SLOTS`.
- Un attribut ne s'affiche jamais : `{item:gender}` seul est une erreur au chargement,
  il ne sert qu'à un `select`.
- Une forme est du **texte littéral** : une accolade y est refusée.

**Casse.** Une forme s'écrit **comme elle apparaît en milieu de phrase**, noms propres
compris (`"Main Street"`) ; seule la majuscule de début de phrase est ajoutée, par
`lib/announce.js` (voir "Casse"). La convention « noms en minuscules » vaut pour la
`base`.

**Déclaration par langue** — `data/i18n/grammar.json`, hors des domaines de clés (la
parité ne le compare pas). On n'y déclare que ce qu'un gabarit utilise :

```json
{
  "fr": { "forms": ["def"], "attributes": {} },
  "en": { "forms": ["def"], "attributes": {} }
}
```

Un attribut se déclare avec ses valeurs (`"attributes": { "gender": ["m", "f"] }`).
Une forme ou un attribut non déclaré, dans un objet de nom comme dans un gabarit, est
une erreur au chargement : une faute de frappe (`"Def"`) ne passe jamais.

### Listes — `list` (extension)

```
{details, list}
```

`details` est un tableau, rendu par `Intl.ListFormat` de la langue (conjonction) :
« pomme × 2, clé et LED × 3 » / « apple × 2, key, and LED × 3 ».

### Imbrication

Une branche de `plural`, `selectordinal` ou `select` contient du texte, des paramètres
simples, des formes de nom et `#` — jamais un autre bloc (`plural`, `selectordinal`,
`select`, `list`), refusé au chargement. Plusieurs blocs côte à côte dans un même
gabarit sont permis :

```json
fr  "Acheter {count, plural, one {# article} other {# articles}} pour {total, plural, one {# pièce} other {# pièces}}"
```

### Validation

**Au chargement** : `createI18n` compile une fois chaque chaîne de chaque langue et
vérifie chaque objet de formes ; les fautes sont rassemblées (langue, clé, motif, position)
et levées ensemble — l'import de `data/i18n/index.js` échoue, le jeu ne démarre pas.
**Au rendu** : une clé introuvable, un paramètre manquant ou du mauvais type, une forme
de nom absente ne lèvent jamais — le texte s'annonce dégradé, et l'avertissement part
au **journal d'avertissements** (Shift+L en mode debug, voir `doc/entity-model.md`)
ainsi qu'en console. Le moteur l'émet par un seul point, remplaçable
(`setWarningHandler`) ; `main.js` le branche sur `view/debug-warnings.js`/
`reportI18nWarning`. Une même faute n'y est notée qu'une fois tant qu'elle est au
journal.
**Au terminal** : `node tools/verify.js` le fait sur les vraies tables (domaine `i18n`
des vérifications).

## Convention future — dialogues (pas encore construite)

Quand un système de dialogue arrivera, même séparation STRUCTURE/TEXTE que le reste du
projet, et même format JSON pur des deux côtés (même raisonnement que ci-dessus : aucune logique
possible dans une donnée de dialogue) :

- **Structure** (langue-neutre : branches, conditions, effets, références vers des id
  de texte) : `data/dialogues/<perso>/<conversation>.json`.
- **Texte** (les répliques, par conversation) : `data/i18n/<langue>/dialogues/<perso>/
  <conversation>.json`.

Granularité = la **conversation** (pas le personnage entier, pas une réplique isolée) :
un fichier par conversation, des deux côtés. Rien de tout ça n'existe encore — cette
section documente juste où ça ira le jour venu, pour que la première conversation
écrite tombe directement au bon endroit.
