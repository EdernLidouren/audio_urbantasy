# data/i18n/ — convention

Données de traduction, éclatées par **domaine fonctionnel** — un fichier par grand
domaine du jeu, un dossier par langue. Le moteur générique (`createI18n`) reste dans
`lib/i18n.js`, inchangé ; ce dossier ne contient que des **données**.

Chaque fichier-domaine est du **JSON pur** (`.json`, pas `.js`) : le format lui-même
interdit toute logique — aucun risque qu'un fichier de traduction accumule un jour du
code. Lisible nativement par n'importe quel outil (Python compris, pour une future
vérification de parité automatisée), cohérent avec le reste de `data/` et avec les
scènes (`scenes/*.json`).

```
data/i18n/
  index.js      # instancie lib/i18n.js avec fr/index.js + en/index.js — POINT D'ACCÈS
                # UNIQUE, importé par toute la vue (view/**, main.js) via `import { t }
                # from ".../data/i18n/index.js"`. Rien d'autre n'importe fr/en directement.
  fr/
    index.js    # charge et assemble tous les domaines fr (fetch, voir lib/i18n.js/
                # loadLocale — même patron que scenes/load.js) en une table plate
    <domaine>.json   # un fichier par domaine : liste dans DOMAINS (index.js),
                     # contenu de chacun dans la table "Où va une nouvelle clé"
  en/
    index.js
    (mêmes noms de fichiers .json EXACTEMENT — voir "Parité" plus bas)
```

Seuls `index.js` (par langue et au niveau racine) restent en JavaScript : c'est le
MÉCANISME de chargement (fetch + assemblage), jamais de la donnée. Les fichiers-domaines
eux-mêmes, `.json`, ne contiennent RIEN d'autre que des paires clé-valeur.

## Où va une nouvelle clé

Chaque fichier-domaine correspond à un **espace de noms de clé** (le préfixe avant le
premier point, avec quelques regroupements assumés — voir la table). Trouve le préfixe
de ta clé, ajoute-la dans **les deux langues**, même fichier.

| Domaine | Fichier | Contenu |
|---|---|---|
| Menus | `menus.json` | Chrome générique de menu (`menu.position`, `menu.toggle.*`), menu principal (`menu.main.*`), pause (`menu.pause.*`), le SHELL Options (`menu.options.*` : titre, entrées de navigation, réinitialisation globale — jamais le contenu d'un sous-écran) |
| Interaction | `interaction.json` | Menu de désambiguïsation (`menu.interaction.*`), retours ramassage/butin (`interaction.*`) |
| Inventaire | `inventory.json` | Sac (`inventory.*`), équipement (`inventory.equipment.*`, `equipment.slot.*`) |
| Objets | `items.json` | Registre d'objets (`item.*`, `core/items.js`) et leurs tags (`tag.*`) — DISTINCT de `entities.json` : un objet ramassable, pas un type d'entité |
| Audio | `audio.json` | Sous-écran Options > Audio (`menu.audio.*`, `audio.*`) |
| Navigation | `navigation.json` | Sous-écran Options > Navigation (`menu.navigation.*`) — inclut l'affichage des coordonnées de la carte (réglage, pas contenu) |
| Sauvegarde | `save.json` | Sous-écran Options > Sauvegarde (`menu.save.*`) + mécanisme de sauvegarde/import partie (`save.*`) |
| Statut | `status.json` | Annonces d'état à la demande (`time.*`, `money.*`, `position.*`, `side.*`) + vocabulaire calendaire (`time.season.*`, `month.*`, `weekday.*`) |
| Scènes | `scenes.json` | Noms de scène (`scene.<id>.name`), annoncés à l'arrivée et par Retour arrière |
| Entités | `entities.json` | Types d'entité (`entity.*`), familles d'entités à textes par instance (`door.*`, `passage.*`, `mirror.*`, `magic_mirror.*`, voir ci-dessous), instances spécifiques (`object.*`, `npc.*`) — chaque type/instance est un NAMESPACE, jamais une clé plate : nom sous `<namespace>.name`, description sous `<namespace>.description` (voir `entity.nameKey`/`descriptionKey`, `doc/entity-model.md`, CLAUDE.md/"Modèle d'entité") |
| Carte | `map.json` | Carte de la ville (`cityMap.*`) |
| Perception | `perception.json` | Perception surnaturelle (`perception.*`) |
| Météo | `weather.json` | Moteur météo (`weather.*`) — noms d'état + gabarit d'annonce (voir core/weather.js) |
| Collections | `collections.json` | Onglet Collections et annonce de découverte (`collections.*`), textes des collections et de leurs entrées (`collection.<id>.name`, `collection.<id>.entry.<objet>.name`/`.description`, déduits des ids — voir `doc/collections.md`) |
| Boutique | `shop.json` | Point de vente (`shop.*`) : menu d'actions, menu à sliders commun (`shop.adjust`, `shop.detail`, `shop.list.*`, `shop.confirm.*`, `shop.discard.*`), vente (`shop.sell.*`), achat (`shop.buy.*`) — voir `view/menus/shop-menu.js` |

### Familles d'entités : l'espace de clés porte le nom du type

Un type dont les instances ont souvent leurs PROPRES textes (une porte précise,
un passage précis) a son propre espace de clés, au nom du type, au lieu de
`entity.*` :

- `<type>.default.name` / `.description` (et autres feuilles, ex.
  `magic_mirror.default.pass_refusal`) : les textes de l'archétype, hérités par
  toute instance qui ne déclare rien ;
- `<type>.<instance>.name` / `.description` : les textes propres à une instance,
  déclarés dans la scène via `nameKey`/`descriptionKey` (ex.
  `passage.town_hall.description`). Une instance ne redéclare jamais une clé qui
  ne ferait que répéter le défaut.

Familles actuelles : `door`, `passage`, `mirror`, `magic_mirror`. Un type de la
famille `door` (échelle, par exemple) garde `door.*`. Les autres types restent
sous `entity.<type>.*`. Renommer une clé : voir `doc/save.md` (table
`config/save-renames.js`).

Aucune clé ne doit apparaître dans deux fichiers-domaines de la même langue (chaque
domaine est un espace de noms disjoint) — `fr/index.js`/`en/index.js` les assemblent
par simple fusion (`Object.assign`, voir `lib/i18n.js`/`loadLocale`), un doublon
écraserait silencieusement l'un des deux.

Un domaine qui grossit trop, ou une nouvelle famille de clés qui ne rentre nulle part
proprement : crée un nouveau fichier plutôt que de forcer un domaine existant — même
règle que l'inverse (ne jamais créer un fichier pour une poignée de clés qui ont
clairement leur place ailleurs).

## Casse : noms en minuscules, phrases normales

Les **noms** s'écrivent en minuscules : tout ce qui désigne une chose et peut
s'insérer dans une phrase — `<namespace>.name` (entités, portes, objets, scènes,
collections et leurs entrées, améliorations), libellés d'objets
(`item.combat_boots`), emplacements d'équipement (`equipment.slot.*`),
étiquettes (`tag.*`), mois, jours, saisons, états météo. Seule exception : un
mot qui garde sa majuscule partout — sigle (`LED`, `EPROM à fenêtre`) ou nom
propre (`Hall effect sensor`, `statue de Matasîle`).

Les **descriptions** et autres textes sont des phrases correctes, majuscule et
point compris.

La majuscule de tête est remise à la SORTIE, en un seul point :
`lib/announce.js` capitalise la première lettre de chaque annonce. Un nom qui
ouvre une ligne (« pomme : un fruit. ») s'annonce donc « Pomme : un fruit. »,
sans qu'aucun écran ni gabarit n'ait à s'en soucier.

## Parité fr/en

**Même nom de fichier des deux côtés, toujours** (`fr/inventory.json` ↔
`en/inventory.json`) — c'est ce qui rend une vérification de parité triviale : les deux
dossiers doivent lister exactement les mêmes fichiers, et chaque paire doit porter
exactement le même ensemble de clés (valeurs différentes, bien sûr — c'est le but).
Une clé ajoutée dans une langue sans son pendant dans l'autre est un bug de contenu,
détectable par un simple diff de clés fichier par fichier — en JSON pur, ce diff peut se
faire avec n'importe quel outil, y compris hors JavaScript (Python, jq, etc.).

**Outil de vérification** : `tools/check_i18n_parity.py` (langue de référence `fr`) —
liste précisément les clés manquantes/orphelines/vides par fichier, écrit un rapport,
code de sortie non nul si une divergence existe. À lancer après tout ajout/renommage de
clé, avant de considérer une tâche touchant l'i18n comme terminée.

**Clés triées par ordre alphabétique**, dans chaque fichier : chaque famille de clés
(`door.*`, `entity.*`, `passage.*`...) reste ainsi d'un seul bloc, facile à parcourir.
Un fichier non trié est une divergence pour l'outil. Pas besoin de chercher la bonne
place à la main : ajoute la clé n'importe où, puis lance
`python tools/check_i18n_parity.py --sort`, qui réécrit les fichiers dans l'ordre
attendu (même format) avant de vérifier.

## Convention future — dialogues (pas encore construite)

Quand un système de dialogue arrivera, même séparation STRUCTURE/TEXTE que le reste du
projet (voir CLAUDE.md, "Réglages en cascade" pour le même principe appliqué ailleurs),
et même format JSON pur des deux côtés (même raisonnement que ci-dessus : aucune logique
possible dans une donnée de dialogue) :

- **Structure** (langue-neutre : branches, conditions, effets, références vers des id
  de texte) : `data/dialogues/<perso>/<conversation>.json`.
- **Texte** (les répliques, par conversation) : `data/i18n/<langue>/dialogues/<perso>/
  <conversation>.json`.

Granularité = la **conversation** (pas le personnage entier, pas une réplique isolée) :
un fichier par conversation, des deux côtés. Rien de tout ça n'existe encore — cette
section documente juste où ça ira le jour venu, pour que la première conversation
écrite tombe directement au bon endroit.
